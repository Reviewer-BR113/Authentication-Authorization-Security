Role-Based Access Control

Give users roles, give roles permissions — and let routes ask only for permissions.

5a

Three roles, four routes, one map

Each cell is a real status code from go run ./demos/05. Fill the matrix one role at a time.

internal/authz/rbac.go
type Role string
type Perm string

const (
    RoleUser      Role = "user"
    RoleModerator Role = "moderator"
    RoleAdmin     Role = "admin"
)

const (
    ReadProfile Perm = "profile:read"
    DeletePost  Perm = "post:delete"
    ListUsers   Perm = "user:list"
    SetRole     Perm = "user:set_role"
)

var rolePerms = map[Role][]Perm{
    RoleUser:      {ReadProfile},
    RoleModerator: {ReadProfile, DeletePost},
    RoleAdmin:     {ReadProfile, DeletePost, ListUsers, SetRole},
}

func Can(r Role, p Perm) bool {
    for _, have := range rolePerms[r] {
        if have == p {
            return true
        }
    }
    return false // unknown role or perm: deny
}
→Routes ask for permissions, not roles. Adding a "support" role is one new map line — no route changes.
→Typed Role / Perm constants — a typo is a compile error, not a silent 403.
✓Default deny: anything not in the map — even a role called superuser — gets nothing.

5b

The middleware that enforces it

It runs after RequireAuth, reads the role from the claims and answers 403 on its own.

internal/authz/middleware.go
func RequirePerm(p Perm, next http.Handler) http.Handler {
    fn := func(w http.ResponseWriter, r *http.Request) {
        c := auth.ClaimsFrom(r.Context())
        if c == nil || !Can(Role(c.Role), p) {
            http.Error(w, "forbidden", 403)
            return
        }
        next.ServeHTTP(w, r)
    }
    return http.HandlerFunc(fn)
}

// wiring: authenticate first, then authorize
protect := func(p Perm) http.Handler {
    return auth.RequireAuth(RequirePerm(p, h))
}
mux.Handle("GET /me", protect(ReadProfile))
mux.Handle("DELETE /posts/{id}", protect(DeletePost))
mux.Handle("GET /admin/users", protect(ListUsers))
mux.Handle("PATCH /admin/users/{id}/role", protect(SetRole))

→Order matters: RequireAuth outside, RequirePerm inside — so no token is 401, wrong role is 403.
→The role lives in the JWT, so a demotion takes effect at the next refresh (≤ 15 min). Need it instant? Deny the jti (session 04).
→Hiding an admin button in the UI is not access control — the server check is.
Mistake

Letting users send their own role, e.g. {"role":"admin"} in the register body. Roles are only ever set by an admin endpoint guarded by SetRole.
